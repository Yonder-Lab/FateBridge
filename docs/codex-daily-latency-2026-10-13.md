# Codex 日常对话：耗时拆解与优化

后续已定位调用前的隐藏工具检索，将两次检索合为一次；保持原模型与 high 强度的最新事业首答为 32.00 秒、调用前 17.82 秒。三次修复后首答的调用前范围为 17.82–23.76 秒。具体往返与完整证据见[工具加载复测](codex-tool-loading-2026-10-13.md)，本报告保留前一阶段结果。

本轮使用桌面版自带的原生 Codex `0.162.0-alpha.17.2`、已保存的全量 FateBridge MCP 配置和同一个 `gpt-6.1-sol`，记录实际多轮对话。日常咨询的修复落在工具描述、结果契约、首轮字段和可直接使用的咨询工作目录中；最终复测没有通过脚本注入咨询角色或强行覆盖推理强度。

## 能拆到哪一层

| 观测 | 来源 | 可以证明的范围 |
| --- | --- | --- |
| 宿主启动、线程准备 | 原生 JSON-RPC 起止 | 本地初始化与 RPC 等待；不等同于模型连接完成 |
| 插件就绪 | `mcpServer/startupStatus/updated` 接收时间 | FateBridge/其他插件的公开启动状态；初始化可与首轮等待重叠，不能相加 |
| 上游处理量 | `thread/tokenUsage/updated` 的数值用量 | 每次累计用量变化、输入、缓存输入、输出与报告的推理 token；不是唯一上下文大小 |
| MCP 往返 | `item/started`、`item/completed` 与原生 `durationMs` | 模型发起之后到宿主收到结果；包括本地执行与协议开销 |
| 计算执行 | `run_metadata.duration_ms` | 业务执行边界，早于最终投影和传输 |
| 最终答案输出 | `agentMessage` 的 `final_answer` phase 和 delta 时间 | 区分“正在查看”的进度消息、最终答案首字与完成 |

原生协议没有提供远端排队、预填充、模型内部推理及网络传输的独立计时。本报告把它们保留在“宿主/上游处理”边界，不把剩余等待都叫作推理，也不把推理 token 为零解释为模型没有任何内部处理。

前一轮观测没有处理 `threadId=null` 的宿主级通知，遗漏了插件启动状态。这次补齐了过滤，同时按实际接收时间计时，不把 RPC 队列中迟到通知的处理时间误当事件发生时间。只保存数值计时与用量，不保存推理正文、启动日志中的凭据或后台命令读取的本地内容。

## 默认聊天为什么超过一分钟

本轮修复前，同一事业问题完整答复 **93.00 秒**：

| 阶段 | 时间 |
| --- | ---: |
| 用户输入至首个 MCP 发起 | 56.077 秒 |
| MCP 活跃区间 | 0.106 秒 |
| MCP 结束至完整回复 | 36.818 秒 |
| 最终答案首字 | 输入后 77.402 秒 |
| 最终答案流式输出至完成 | 约 15.60 秒 |

累计记录 5 次不同的上游用量更新，输入 **181,146 token**，其中 **146,176** 为缓存输入，报告的推理输出仅 **453 token**。同一段历史可能在多次响应中重复计入，不能说单次上下文有 18 万 token。可见宿主活动包括两项记忆/工作区查询，而只有一项实际业务 MCP 调用。

没有背景查询的高强度咨询对照也有 5 次上游用量更新。可见业务调用之外的处理仍存在，公开协议没有标明每次隐藏请求的具体用途；不能把所有更新都称为 MCP 发现，或推断每个请求耗时的服务端组成。

在有启动通知的对照中，线程的 FateBridge 就绪约需数秒。例如高强度咨询第一次线程的插件启动约在输入后 4 秒完成，MCP 却直到约 32.54 秒才发起。这轮证据不支持把一分钟等待主要归于 Python 服务启动。其他插件曾返回失败状态，本轮保留原配置并只记录状态，没有将这些失败归因于 FateBridge，也没有关闭用户其他插件。

补齐出生时间的修复前对话用了 **86.51 秒**。模型先调用综合时运，再覆盖事业参数；事业投影报错后又补调用。三个 MCP 活跃区间合计只有约 **0.12 秒**，两次调用之间约 **28.67 秒**，末次调用后约 **32.54 秒**。累计上游输入 **317,092 token**，其中 **276,480** 命中缓存。这里可直接修复的是多余业务步骤和错误恢复往返。

## 已落地的日常修复

1. **描述明确专项工具已有时机依据。** 八字专项本来就按出生资料和分析日期自动推算大运、流年。原描述强调“可传大运柱”，容易诱导先调用时运再手动覆盖。现在明确自动计算与覆盖参数的适用范围，普通首轮直接调用专项工具。
2. **显式覆盖仍返回来源。** 两个柱都被覆盖时，旧服务没有返回 Schema 已声明的 `timing_context`，严格投影因此拒绝合法首轮路径。现在返回明确的 `explicit_pillar_overrides` 和覆盖标记，不编造自动起运年龄或分析日期，不修改数值计算。
3. **当前时间依据与全年时间线分开读取。** 首轮时间视图保留当前大运/流年/流月、分析时间、太阳时调整、时区与节气边界，移除全年完整网格。相同输入的实际 MCP 返回从 **137,556 字节降至 10,226 字节**；完整业务摘要 SHA-256 相同，当前大运和节气边界一致。完整时间线仍可按需请求。
4. **普通回复聚焦问题。** MCP 指令与咨询目录说明首轮约 200–300 字，返回关键结论、依据和行动建议，深入问题再扩展。回执留在工具结果中，普通用户不必阅读长编号；精度警告仍需说明。
5. **正常加载的咨询工作目录。** [`consultation/AGENTS.md`](../consultation/AGENTS.md) 定义自包含咨询，缺信息先问，不查询无关历史或代码。该目录的 `.codex/config.toml` 设置中等推理强度，保留原模型、插件和 87 项全量 MCP。原生 `thread/start` 实际报告了该指令文件与 `medium`，最终运行没有 `--consultation-role` 或 `--effort` 覆盖。普通根目录开发聊天的全局 high 设置未修改。

普通默认临时聊天仍有背景查询，故进一步在仓库根目录增加按任务分支的 `AGENTS.md`：普通咨询进入当前资料的咨询流程，开发/排错仍保留工程历史和测试流程。它不改变根目录的全局 high 推理设置。新增根目录复测同样由正常指令加载完成。

中间复测还发现一句“时间未知时按未知范围分析”会让人误以为已有无时盘接口，已改清楚：无法确认出生时刻时不排确定盘，只能先提供不依赖命盘的现实建议；最终复测再次检查此处。

## 没有采用的提速方式

当前原生宿主启用了 `code_mode_host`。本轮在单独进程中关闭它做对照，模型答复变快，但工具调用环境不可用，没有实际 FateBridge 计算。**这是功能退化，验收不通过**；没有写入日常工作目录配置，也没有计入成功计算的性能比较。

同一工作目录的高强度事业对照为 **49.79 秒**，中等强度的中间版本首答为 **64.02 秒**。它们受缓存、服务器与模型规划变化影响，并非严格受控实验，不能证明降低强度必然更快。中等强度作为普通咨询的局部默认，不影响代码任务；复杂比较仍可提高强度。

根目录高强度对话正常加载仓库 `AGENTS.md`，事业及缺失时间共 **5 轮**；独立咨询目录正常加载子目录指令与配置，共 **10 轮**。这些最终轮次都没有背景查询、连接错误、资源发现前置步骤或重复计算，全部完成。它们没有脚本的角色、强度或直接工具覆盖。全量连接仍实际发现 87 项工具。

普通临时目录对照仍有三项背景查询，首答为 59.75 秒；仓库根目录正常指令下为 41.96 秒且无背景查询。根目录补齐时间后的回复为 33.27 秒，独立咨询目录为 25.61 秒，均只调用一次事业工具。明确角色应落在日常正常加载的指令中，不能只给验收脚本增加角色参数。

这些是小样本实测，缓存、远端服务和模型规划有变化，不能把秒数差值全部归因于一个改动。此前中等强度首答也曾超过一分钟；尚未建立延迟 SLA。关闭代码模式的失败对照仍单独保存，没有用更快的无工具回答充当验收通过。

全量回归 **1947 passed、88 skipped、7 warnings**；最终定向测试 **52 passed**；FastMCP 3.0.0 最低版本 **49 passed**。Black、isort、mypy（src）和 `git diff --check` 通过。工程源代码与固定测试副本逐文件一致；根目录 AGENTS 在单元套件之后新增，由原生根目录对话另行验证。未运行 Linux CI。

证据见 [validation.json](audits/2026-10-13/codex-daily-latency/validation.json)、[投影前后摘要](audits/2026-10-13/codex-daily-latency/projection.json) 和各阶段原始 JSON。使用方法见 [Codex 指南](codex-guide.md)。本轮没有重启或埋点现有桌面窗口，而是用桌面版原生运行时创建临时真实对话、加载日常正常指令和配置。已有 GUI 对话不会因此自动切换工作目录或重新加载指令；新聊天应确认实际工作目录。
