# 实际 Codex 桌面新聊天的调用前等待

进一步核对宿主日志语义、只读原生采样与项目预热试验见 [首次宿主准备与双人复测](codex-host-preparation-2026-10-13.md)。其中缓存目录明确不等待启动，世界状态日志仅表示开始；本报告的整体时长保持为前一轮历史证据。

2026-10-13 在实际 Codex Desktop 宿主创建了 5 个持久新聊天、完成 9 轮日常对话。保持桌面原生 CLI `0.162.0-alpha.17.2`、`gpt-6.1-sol`、high、原插件配置和完整 FateBridge 工具范围。两项最终新聊天没有传入模型或推理强度覆盖，原生记录仍确认使用原模型和 high。

本轮修复后事业首答的完整回复为 30.898、30.217 秒，业务调用前为 15.531、17.552 秒；双人首答仍需 23.234 秒才调用。不能宣称所有等待已消除。稳定的结构变化是常用咨询由“检索定义→计算→解读”三次上游请求变为“计算→解读”两次，没有降低推理强度或删掉计算依据。

## 如何确认这是桌面聊天

通过 Codex 自身的创建聊天接口在已保存的 FateBridge 项目创建正常本地聊天，并打开桌面主窗口。它们保存在原生线程数据库和会话记录中，`originator=Codex Desktop`，工作目录为仓库根目录，逐轮记录模型与 high；`source=vscode` 是原生协议的来源枚举。没有另外启动临时 app-server，没有脚本咨询角色或实验观测开关。创建接口的第一项带有原生转交消息包装，测试资料为虚构人物，未在用户消息中提示工具名称、预期答案或调用步骤。

电脑使用工具禁止自动操作 Codex 本身，因此本次使用官方应用接口创建、打开、追问和读回真实持久聊天。没有测量鼠标点击到窗口绘制首字的时间，不能把原生 turn 的时长称为 GUI 像素计时。最后已打开“FateBridge 桌面默认设置事业复测”，全部聊天保留供查看。

## 从第一性原理拆分

延迟来自串行依赖的边界，而不是工具数量本身。本地检索执行只有约 9 毫秒，但模型为了决定检索、接收检索结果和随后构造计算调用，需要另一轮上游请求。重复传递已知定义是可修复的串行工作。

从只读 `state_5.sqlite`、`thread_history_1.sqlite`、`logs_2.sqlite` 和已选线程的原生会话记录交叉核对。请求准备日志与本地流事件时间来自数据库内时间戳，未使用日志文件写入时间。导出仅含时间、数值、工具标识和线程来源，绝不导出原始日志正文、私有推理、凭据或无关聊天。

同类事业小样本的完整回复降低约 2–3 秒，但不能把全部差值归因于本次修复。宿主准备、缓存、网络、上游服务及模型计划波动很明显；部分短追问与新聊天有时间重叠，未构成专用空载性能基准。上游轮数减少是逐轮代码标识与请求日志共同确认的结果，不是根据回复秒数推断。

修复前事业的 17.386 秒可以进一步按不重叠边界拆为：宿主准备 6.045 秒、第一次请求至检索代码完成 5.333 秒、结果返回与下次请求准备约 0.210 秒、第二次请求至业务调用 5.798 秒。检索本身的 9.071 毫秒被包含在相应宿主窗口内，不能再加一遍。

### 宿主准备

新聊天首次请求准备为 6.045–10.132 秒，同一聊天后续轮次为 0.170–0.515 秒。说明这段是首次会话准备的显著成本，而不是每次 FateBridge 计算的固定耗时。

事业 A 在输入后 4.677–6.405 秒记录了 24 个其他 MCP 的启动失败，其中含缺认证、未知启动错误和缺文件；没有 FateBridge 失败。它们与技能、配置、工具目录和会话准备并行发生，不是可相加的 24 段等待。现有观测无法独立算出各插件对关键路径的贡献，因此没有为了加快 FateBridge 而禁用用户其他集成。

实际桌面使用延迟工具世界状态，代码模式预热关闭；这与自行启动的临时宿主默认值并不完全相同。没有更改全局特性、删除技能、改变认证或重启正在使用的桌面进程。仓库修复能够减少模型往返，无法在仓库内修复桌面宿主内部的首次会话准备。

### 远端排队与模型处理

事业 A 第一请求准备到首个本地流事件为 3.275 秒，到业务调用为 7.477 秒；事业 B 分别为 3.157、10.834 秒。双人首答分别为 5.840、13.102 秒。首个事件可能是进度消息或推理项元数据，不是最终答案首字，也不是服务端首 token 计时。

本地只有客户端请求准备和接收边界。链路包含网络、远端排队、上下文处理、模型推理、代码生成及本地调度，无法将其中任何一段命名为纯模型耗时。已检查相关进程/线程时间窗口，没有 `openai-processing-ms`、`server-timing`、队列或预填充指标。实际链路记录为 Responses WebSocket；通用 HTTP 响应头文档不能替代本次链路的实测。观察器将 `remote_queue_ms` 与 `model_processing_ms` 显式写为 `null`。

[OpenAI Codex 观测文档](https://learn.chatgpt.com/docs/config-file/config-advanced)提供请求、流事件与工具边界的遥测；[API 文档](https://developers.openai.com/api/reference/overview)说明 HTTP 处理时长头。两者都不能凭现有本地记录独立还原本次远端队列与模型内部阶段。进一步拆分需要服务端提供对应时间或宿主导出服务端指标。当前桌面 trace 导出默认关闭；开启全局导出和重启会影响其他工作，本轮未作此修改。

## 已落实的修复

- 根目录项目指引正常加载三项常用 MCP 的完整输入约束与共享首轮字段，资料齐全可直接调用；其他工具和不明确参数仍查询实际定义。只删 Schema 的标题和说明，保留参数、默认值、必填、范围、引用和服务端验证。没有提供测试人物或预期解读。
- `scripts/build_codex_call_contracts.py` 从实际 FastMCP 工具列表和共享 catalog 生成，`--check` 加测试防止接口与项目指引漂移。保留完整服务端输入/输出 Schema，全部工具继续公开。此优化适用于正常加载该项目指引的新聊天，其他工作目录仍可能需要一次发现。
- 一般关系采用 `general`，缺时刻先问，时刻撤回时撤回确定结论；沿用实际返回的日期、精度、计分口径及自动时运依据。不得拿接口默认值替用户补出生时间。
- `scripts/observe_codex_desktop.py` 对指定的持久桌面线程作只读计时导出。不开启实验 API，不修改遥测设置，也不运行模型。隐私隔离测试覆盖原始日志、推理、参数中的凭据哨兵，以及只读数据库防写入。

## 真实对话读回

共 5 个桌面新聊天、9 轮完成，无业务工具错误或连接失败。本轮发现的无关插件启动失败单独记录，不算 FateBridge 全局宿主健康通过。

| 桌面标题 | 轮次 | 实际表现 |
| --- | ---: | --- |
| FateBridge 桌面真实咨询复测 | 2 | 旧流程事业首答一次检索、一次计算；追问辞职时复用结果，1 次请求、零计算，区分传统依据与现实决定 |
| FateBridge 桌面直接调用复测 | 1 | 2 次请求、零定义检索、一次事业计算，保留时运与创业依据 |
| FateBridge 桌面双人相处复测 | 2 | 首答直接 general 合盘；追问解释综合 54.5 与净分 8 的口径差异，区分合、刑的条件和现实建议，零重复计算 |
| FateBridge 桌面缺失信息复测 | 3 | 缺时刻先简短询问，零工具；补齐后直接事业计算；撤回确定时刻后明确不能沿用确定排盘，零工具 |

所有需计算的新流程轮次均为两次请求；不需计算的追问均为一次请求。手工读回确认实际依据、分数口径、信息追问和确定性边界符合要求；这不等于保证模型以后每次回答措辞相同。
