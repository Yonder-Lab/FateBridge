# Codex MCP 等待与异常：根因定位及优化

本轮把连接、发现、计算、解释分别计时。可确认的主要问题在工具契约的表示、模型获取信息的流程、验收宿主生命周期，以及咨询任务的上下文角色。计算本身是毫秒级；剩余的大部分等待发生在 Codex 模型/宿主阶段。

已修复所能控制的流程和契约问题。旧路由失败定位到 Codex 工作区/账户路由发现阶段，历史记录没有底层网络细节，不能断言是 DNS、限流或服务端故障，也不能宣称已经根治。

## 先确定每一层负责什么

| 层次 | 责任 | 本轮证据 |
| --- | --- | --- |
| Codex 宿主与账户连接 | 启动、工作区路由、模型请求、插件就绪 | 旧失败返回 `workspace routing discovery timed out`，当时没有 MCP 调用 |
| 任务角色与模型规划 | 识别问题、确认缺口、选择必要证据 | 默认代码角色仍查询记忆/目录；显式独立咨询角色不查询 |
| MCP 发现与契约 | 发布可调用参数、输出结构、首轮字段建议 | 原先要求额外资源读取，输出 Schema 重复展开 |
| FateBridge 执行 | 验证输入、计算、投影、运行回执 | 最终合盘调用约 51 ms，补齐出生时间后的两项调用共约 73 ms |
| 模型解读 | 将返回字段转成普通中文，保留依据和范围 | 对应完整回复仍需约 72–93 秒，不能全部归因于本地计算 |

这里的“模型/宿主阶段”是合并边界：没有服务端细分计时，不能把剩余时间全部称为模型推理。Schema 字节数是实际传输/状态清单体积，也不能直接换算成模型输入 tokens。

```mermaid
flowchart LR
    U[用户问题与已确认资料] --> G{信息足够}
    G -->|否| Q[一次简短追问]
    G -->|是| S[已发布的工具描述与参数 Schema]
    S --> T[一项主证与必要旁证]
    S -.仅有缺口时.-> D[按需读取资源]
    D --> T
    T --> C[本地验证、计算、投影、回执]
    C --> R[中文解读与依据]
    R -.验收结束后.-> A[独立收集全插件状态]
```

## 找到的根因和具体修复

### 1. 已有契约又要求重新发现，制造串行模型往返

旧 MCP 初始化指令和使用指南要求先读场景，再读输入契约。工具其实已经发布了参数 Schema，但首轮字段建议只存在资源中。模型为完成这些步骤需要多轮决策和工具交互，每轮都有宿主/模型开销。

现在将共享数据中的 `suggested_fields` 直接加入工具描述；参数与描述够用时直接计算，仅有选择、参数或深层字段缺口时再读资源。14 个首轮视图通过真实严格投影调用测试，CLI/资源/工具描述共用同一份数据。

自然语言复测中，常规事业、补齐时间和关系问题均直接计算，**资源发现/契约读取调用降为 0**。事业案例从三项业务调用降为一项，仍回答工作方式、时机和创业倾向；用户需要更多粒度时再补旁证。

### 2. 展开共享 Schema，重复传输相同结构

原中间件对非递归 Schema 做 `dereference_refs`，使快照、回执等共同结构在多个位置重复。原生宿主清单中 FateBridge 的 87 个工具约 **4,305,860 字节**。

现保留标准 JSON Schema 的 `$defs/$ref`，不移除输入/输出契约，不修改计算或字段类型。相同原生宿主统计降为 **2,199,499 字节**，减少约 **49%**。输出 Schema 本身从约 3.94 MB 降至 1.84 MB。

所有已发布输入/输出 Schema 均通过 JSON Schema 检查，输出与原始 Pydantic Schema 一致。当前依赖和 FastMCP **3.0.0** 最低版本均通过实调用测试；原生 Codex 已成功消费新 Schema。

### 3. 首轮字段少了回答所需依据，造成重复计算

中间关系复测第一次只取小结、优势、挑战和一项传统维度，随后为了讲清原因又请求完整分析、建议和五行关系，重复执行相同输入。

首轮视图现保留完整分析依据、人物信息、建议与口径，仍移除重复快照。最终相同问题只调用一次双人分析，没有为了补解释再计算。优化目标是“回答当前问题所需的信息完整”，不能只追求最小字节数。

### 4. 模型擅自把未知关系选成婚姻

中间复测明确传入了 `relationship_type="marriage"`，用户只说“我们两个人”。接口原本默认已是 `general`；问题发生在模型显式选择参数，不能误诊为服务器默认值错误。

旧描述突出“合婚”，示例也使用婚姻类型。现参数说明、工具摘要、初始化指令与虚构示例共同明确：用户未说明时保留 `general`，不能从性别推断关系类型。

最终真实复测明确使用 `general`，返回整体 **54.5/100**，并正确解释净分 +8 与独立传统维度 39/100。测试同时保留显式婚姻案例的 **51.1**，确认计算算法没有改变。

### 5. 验收生命周期与日常使用不一致，诊断又挡住回复

旧脚本每个案例重新启动整个 Codex 宿主；上一轮多组复测还曾重叠运行。重复冷启动增加账户路由与插件初始化机会，但没有证据证明它就是旧路由失败的唯一原因。

现整组案例复用一个宿主，案例使用独立临时对话，模型清单只读一次；不重写用户模型或全局配置。通知按线程/轮次过滤，避免前一聊天的迟到通知混入下一聊天。

实测第一次 `mcpServerStatus/list` 等待全部插件清单耗时约 **45.35 秒**。这属于验收诊断，不应成为答复前置条件。已移至**所有用户轮次结束后**，且诊断失败不会覆盖已完成对话。调整过程中缺时间案例从宿主启动到首个完整回复约 **33.14 秒**；这是验收脚本路径的观测，不是桌面 UI 提速承诺。

### 6. 连接失败没有清晰的等待边界和归因

本机原生 CLI 的 `unbounded_connection_retries` 为启用状态。旧验收只设六分钟总期限，无法尽早区分宿主重连、无进展和计算中的未知状态。

现验收进程临时关闭无限重试，并分别设置总时长、无进展和重连次数边界；超过预算中断该轮，保存已完成公开活动与错误，不自动重复业务请求。全局桌面设置没有修改。

计时记录包含首个模型活动、首个公开输出、MCP 起止、后台查询类别和重连次数。故障注入验证：三次重连在 30 秒归为宿主连接问题；MCP 已开始但没结束时保留 `mcp_inflight_unknown`，不武断认定计算失败；持续推理活动不会被误判为空闲；RPC 等待不超过剩余预算。

### 7. 咨询角色与代码任务的上下文应明确区分

默认 Codex 的较高优先级记忆/工作区指令仍会触发查询，MCP 指令无法覆盖它们。删除用户全局记忆设置会影响其他代码任务，不能作为 FateBridge 的修复。

新增可选 `--consultation-role`，为临时对话明确声明：当前是由当前消息提供虚构资料的独立咨询，不需要仓库或历史事实。它通过原生 `developerInstructions` 设置任务角色，不预选工具、不提供答案，仍使用原有 `gpt-6.1-sol` 和 high 强度。

两轮事业、两轮日期纠正和当前工作区的两轮关系复测均无记忆/目录查询，实际计算与解读正常。事业首轮仍耗时约 **69.41 秒**，因此只能确认额外查询被消除，不能宣称这个角色让所有回复更快。桌面默认聊天也不会因验收选项自动切换角色。

## 验收结果与证据

共记录 **21 轮原生对话完成**，串行运行时无重连或路由失败；中间两轮关系对话存在上述类型选择问题，已经单列，不能等同于语义验收通过。最终补齐时间、一般关系、独立咨询角色和日期纠正均通过。

- 全量回归：**1943 passed、88 skipped、7 warnings**。测试使用固定副本，当前源代码与副本逐文件一致。另一项并行接口清理移除了旧入口及其测试，因此与清理前快照的 1952 通过、89 跳过不同；两份回执分开保存，不能把数量变化当成测试失败。当前注册配置的 MCP 仍实际发现 87 项工具，新增关系复测返回 `general`、只计算一次。
- 当前依赖定向测试：**60 passed**；最低 FastMCP 3.0.0：**47 passed**。
- Black、isort、mypy、`git diff --check` 通过。macOS 跳过的 Golden 等测试不代表本轮已跑 Linux CI。
- [validation.json](audits/2026-10-13/codex-mcp-root-cause/validation.json) 汇总阶段、Schema 大小与边界；各阶段 JSON 保留真实参数、公开回答、回执和计时，省略推理流及无关本地文件输出。
- [上一轮失败记录](audits/2026-10-13/codex-mcp-dialogue/host-failures/registered-invalid.json)继续保留，没有被本轮成功覆盖。

目前仍无法从历史日志进一步判断旧工作区路由失败的底层网络原因。新流程减少了不必要工作并有明确失败边界，本轮复测没有再复现；这不证明远端路由服务或桌面整体延迟已被永久修复。
