# 工位照片咨询的体验根因审查

日期：2026-10-14。源码基线：8b2e751。本报告审查当前聊天的完整咨询过程；没有修改计算逻辑、咨询指引或测试，没有提交或推送。

## 结论

用户请求是：结合个人出生资料和真实工位照片，从风水/玄学角度说明布局是否应调整，并在不能搬桌、不能转向的条件下，对手机、瓶子、摆件、绿植给出可实施且有理由的方案。

实际交付是：个人命卦的书桌朝向判断、三项现代作者室内形态检查、针对朝向星元素的条件式代表物，加上一份由模型生成的桌面整理方案。前三项计算没有发现结果错误，但它们不足以支持最后那份具体物件摆放方案。体验不完整是能力范围、事实采集、咨询决策和验收目标之间没有衔接；不能仅归因于模型太保守，也不能靠放松依据要求来修复。

## 当前聊天发生了什么

| 阶段 | 实际输入/动作 | 对用户任务的贡献与缺口 |
| --- | --- | --- |
| 首轮照片与出生资料 | 发现工具；额外查找资源读取工具、列模板、读取 input；调用 assess，methods=[bazhai]，只有书桌朝西和单人出生输入 | 得到西向五鬼火、候选北/东/东南/南。没有读取建筑坐向、桌位落宫、桌面物件、窗户关系；不是完整勘察 |

原咨询阶段共有3次 assess 计算、5次工具/资源发现操作；不是5次发现都必要，第一次读取 input 有理由：代码模式展示的 placements 类型是 unknown 交集。补充事实后的再次发现则重复。此次审计新增的复核调用不计入原咨询。

## 根因一：已实现的规则范围小于“工位布局审查”的承诺

`Placement.purpose` 只接受 door/bed/desk/stove，位置要求相对全宅中心的落宫；没有手机、瓶杯、玩偶或植物的桌面坐标输入。FormObservation 只承载入口位置/视野/直线、背靠/距离、镜面。实际 form_rules 仅检查入口可见、避开直线、实体背靠三项。

证据：`src/fatebridge/core/fengshui/models.py:166`、`layout_inputs.py:29`、`src/fatebridge/data/fengshui/layout-supplements-v1.json:107`。本次本地探针确认 purpose=phone/plant 被拒绝，can_move/desktop_objects 也被拒绝。

这不意味着必须把所有物品都硬塞进 Placement。需要先定义有来源的物件规则、桌面与全室参考系，以及它们适用的范围。目前没有完整梁柱/尖角/走道/门窗组合判断，也没有自动照片几何解析，不能由模型自行补齐。

## 根因二：计算结果与行动方案之间缺少可检查的推导

`analyze_layout` 输出方向候选和元素关系；`evaluate_element_targets` 根据调用方选定 support/drain、已计算星元素以及用途校验，返回代表物和跨作用域关系。它没有比较现有瓶杯、植物、手机的材质/位置，也没有给出左右、前后或距离方案。

证据：`layout.py:33`、`layout.py:250`、`layout_supplements.py:159`、`layout_supplements.py:250`。土候选的 application_scope 明确不取消朝向结论、不验证运势效力。

原回复将“保留入口视野”延伸成“手机必须放右、饮水放左、绿植放右后”的细分方案，关联强度不够。即使部分位置有实用理由，也不等于各项都由风水规则导出。正确交付应让每项行动分别注明：引用哪条规则、改善哪个已确认条件、为何适用于这个位置；无法建立对应的项目不能计为风水方案完成。

## 根因三：已知能力边界后，咨询没有继续推进关键缺项

不可搬动的约束处理正确，但随后的流程基本停在“保留入口可见、不要添物”。没有进一步核对真正影响第三项形态判断的实体背靠；没有说明若要开展年盘/宅盘，还需要工位相对明确全室中心的位置、建筑坐向、玄空历史定运等资料。

尤其是原追问将“门口或主要来人通道”并为一项，用户回答左边后，工具直接收到 entrance_position=left。左侧有通道不必然等于房间入口在左。测试可以证明这组参数的正确计算，不能替用户证明它们的现场语义。

不能立即算年盘/玄空并非错误：面朝西不等于位于西宫，缺少落宫时年盘无法关联工位。问题在于没有给用户清楚的分层完成情况和有用的下一步，而将 partial 当成对话的终点。不要为了显得完整而调用所有方法；应补那些会改变实际建议的信息。

## 根因四：出生资料的“个性化”没有解释清楚

当前流程实际采用的是命卦，不是八字喜用分析。`bazhai.py:100` 根据换年后的有效生年与男女起算法求宫数；出生时刻在此用于处理年度边界，不用于八字时柱。此次出生地没有进入风水计算。

新复核展开 layers 后确认是离卦、九宫；原首轮视图没有 layers.bazhai.occupants，因此原答复只有方向名称，没有展示为什么这些方向属于此人的匹配候选。

这不是说凡给出生时间就必须多算一张八字。问题是没有向用户解释究竟用了哪一种个人匹配方法，也没有在用户要求更广泛“风水和玄学”时明确是否要扩展个人命理层。即便另算八字，仍需建立其与布局的具体规则桥接，不能拿五行数量直接推出缺什么、补什么或物件在哪边。

## 根因五：指引有边界要求，却缺少完成任务的流程

AGENTS.md:11 和 mcp_server.py:90 明确要求“不用生活建议代替风水计算”，此次仍在固定工位的条件下给出了大量生活建议。不能归因于指引强迫模型如此回复，这是当前助手执行的缺口。

同时，指引主要列出不猜、保留 partial、分流派、少调用等要求，缺少广泛照片布局请求的正向流程：任务覆盖范围、照片候选清单、关键信息确认、约束内方案推导、剩余任务跟踪。通常200–300字的首轮风格也不能覆盖用户要求逐物件解释的深入任务；需要随任务复杂度展开。

指引应明确：部分计算允许先回答，但任务仍有待解决事项；不能搬桌时应筛选现有有规则依据的动作，并说明确实没有可支持方案的领域及其资料/能力缺口。

## 次要摩擦：调用合同可读性

本次 ALL_TOOLS 的 TypeScript 展示将 placements 呈现为 unknown 的交集。源码 transports/mcp.py:126 已内联引用，且模型的交叉字段 allOf/anyOf 校验存在，因此不能据此断言 MCP 原始 Schema 没有字段。更可能需要核查宿主对复杂 JSON Schema 的渲染/连接合同转换，具体责任点本次未确定。

生成的免发现调用合同只覆盖 bazi_career/two_person_compatibility/timing_analysis（scripts/build_codex_call_contracts.py:22），不含 fengshui_assess。本次初次读取 input 合理，后续重复发现可避免。这影响延迟与理解，不是具体摆放建议缺乏依据的主因。

## 验收为何没有捕捉到本次不满意

已有测试与产品文档重视作用域、未知值、输入校验、回执链、跨端一致和作者边界。这些必要条件此次大部分满足，但不足以证明“原用户任务已经解决”。此前产品报告也明确指出了判断到现实行动的缺口，当前指引没有让本次助手稳定跨过这一环节。

需要新增人工体验验收场景：出生资料+照片、固定工位、逐件要求风水摆法、追问为什么。评审每项建议是否有事实和 rule/source、现场入口与通道是否区分、关键缺项有没有后续处理、生活建议有没有替代主任务。对真正未实现的规则，明确解释并停止作出吉凶承诺是正确行为；不能奖励编出更多摆法。范围外的外部宿主测试不应未经授权重新纳入 FateBridge CI；可保留人工体验记录及 FateBridge 自身合同回归。

## 建议修复顺序

1. 先修咨询交付：保留已算的方向/形态，清楚列出本次已覆盖、可补资料、尚未实现的层次；入口与通道分开采集；只追问会影响行动的资料。每项风水建议必须对应规则、作用域、已确认事实和允许动作。
2. 再建规则能力：按选定来源/作者新增实际要支持的形态或物件规则，规定桌面/全室参考系与材质/观察条件。不要为手机、瓶子等各写一条无来源的固定左右处方。
3. 咨询层保存现状、照片候选、目标、约束、候选动作和解释，不改变规则计算的来源边界。几何规划若另行实现，需要可验证的尺寸、通行和碰撞输入。
4. 验收分开看：规则计算正确、REST/MCP/CLI一致、连接工具行为、真实多轮用户体验、传统效力声明。前三项不能替代第四项，更不能证明第五项。
