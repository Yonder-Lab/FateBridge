# 全面自我画像（Onda）

给用户一份能回看、能用自己的经历对照的画像：哪些特点有盘内依据，哪些只是某一体系的描述，哪些现实安排值得尝试。按生活问题组织，三套盘不应变成三份重复报告，也不必每个维度都凑齐三家意见。

## 引用路径与必读资料

发现入口可能是软链接。先进入入口目录，以 shell 内建 `pwd -P` 取得真实目录，再解析相对引用；不要裁剪 `.agents/skills/onda-*` 的字符串父目录。

- 计算与完整结果交付：[../_shared/fatebridge-engine.md](../_shared/fatebridge-engine.md)
- 表达与事实边界：[../_shared/onda-counsel.md](../_shared/onda-counsel.md)
- 场景取舍与去重：[../../docs/scenario-routing.md](../../docs/scenario-routing.md)

所有干支、十神、喜用、安星、行星与运限由引擎计算。各体系是文化解释视角；共同描述不构成独立统计证明。

## 输入与覆盖

使用当前聊天已确认的出生公历日期、小时／分钟、性别、地点与出生时区。资料完整的独立咨询不查项目历史或记忆；用户明确沿用历史时再核对。仅对会影响所选计算的缺项作一次简短核对。

- 出生时刻未知不能擅填 0 或中午。只有时段时保留排盘不确定性；用户明确授权后才比较假设时刻，分别标出稳定与随时刻变化的结论。
- 中式工具默认真太阳时，西占默认记录的民用钟时。共享人物资料，分别构造各工具输入；不能把同一个太阳时开关强灌三系。
- 西占核心盘支持从已支持 `birth_place` 解析可选坐标，核对返回地点、时区与精度即可；关系盘／推运所需坐标以实际 Schema 为准，不能猜坐标。
- 资料不足的体系保留缺失，先交付可以得到的部分。主盘已算过则复用，不为整齐补算；未返回或未读取的维度不能写成已覆盖。

## 主证与补充

明确要求三体系画像且资料齐全时，`analyze_destiny`、`ziwei_birth`、`astro_chart` 为三套主证，可并行计算。用户限定其中两系或要求沿用已有结果时照其范围执行。普通摘要用已验证的 `fields`、`strict_fields=true`、`include_snapshot_text=false`，不先把所有专项跑一遍。

| 想回答什么 | 主证中的实际依据 | 何时补充 |
| --- | --- | --- |
| 性格、处理事情的方式 | 八字 `day_master/ten_gods/structure_profile`；紫微命身宫及相应宫位星曜；西占日月上升与相关相位 | 只有用户需要更深行为分析且主证不够时用 `bazi_personality` |
| 事业、发挥长处的环境 | 八字格局的实际判断依据、紫微官禄宫、西占相关宫位与相位 | 明确要角色／创业／阶段判断时用 `bazi_career`；静态盘不能直接给年份 |
| 感情和相处方式 | 紫微夫妻宫、西占关系相关配置，八字中确有返回的关系依据 | 要桃花／感情时机才用 `bazi_romance`；单人盘不推对方心理或两人适配 |
| 家庭及与亲人的相处 | 紫微相关宫位与已返回的八字六亲依据 | 具体家庭问题用 `bazi_relatives`；现实家庭史以用户确认为准 |
| 当前阶段与时运 | 已有专项的 `timing_context` | 未覆盖而用户确要时运时用 `timing_analysis`；只有深查单步大运才用 `dayun_analysis`（`analysis_age` 按虚岁） |
| 传统健康文化参考 | 不由日主强弱或普通疾厄宫文字直接认定身体状况 | 用户明确要这一层才用 `bazi_health`，并按 onda-jiankang 区分计算、传统对应与生活建议 |
| 原始四柱／命盘核对 | 已有综合结果 | 仅用户要原始命盘时用 `bazi_birth`；不与 `analyze_destiny` 默认重复 |

上表是问题索引，不是六项必调清单。全面画像可以覆盖用户所要的性格、优势与限制、事业、关系、家庭和阶段；健康、财务细论、精确年份与专业推运按问题扩展，不把未算内容写成结论。

## 深度来自可核对的区别

1. **先立清楚本次范围。** 用户已说关心重点就直接进入重点；没有另设必答问卷。资料齐全先算，不能先写一段泛泛性格当结论。
2. **每套主证留住实际结构。** 八字读 `structure_profile.dominant_structure/decision_basis/useful_elements` 与 `element_distribution_basis`，不以最大五行直接当喜用。紫微 `ming_gong/shen_gong` 只给位置，解读星曜须再有 `ziwei_birth.palaces` 中对应宫位的 `stars_detail` 与 `sihua`；本命 `daxian` 列表不等于已算当前动态运限。西占按 `planets` 的 Sun／Moon、`angles` 与相关 `aspects` 读，不能仅用太阳一句话代替整张盘。
3. **按生活主题对照。** 一个主题选两三条有区别的依据，讲它们分别支持什么。共同点可合并并注明来源；单系结果照常保留，不因另两系没讲而自动降成“弱信号”。
4. **分歧本身就是交付。** 先检查日期、太阳时、时区、宫制及出生精度是否不同。输入无误仍有分歧时并列说明，可写「八字较强调……，西占同时强调……，在不同情境下可能表现不同」。没有现实经历支持时，不替用户编出一个情境把矛盾消掉。
5. **把特点落到可以试的安排。** 挑两三项与用户现实目标有关的观察或小尝试，写清它们是生活建议。若用户未给职业、关系或生活背景，使用条件句，不指定行业、伴侣、疾病或现实事件。

如摘要字段不足以回答画像中的某一项，按实际输出合同扩展该项所需字段；已有 `result_delivery` 就读同 run 的窄字段／页面。投影已排除的字段无法靠分页恢复，不能悄悄重排来声称原 run 完整。

西占时运明确指定钟时时传 `analysis_hour/minute` 并核对 `analysis_context.analysis_datetime`；`as_of` 不替代目标钟时。没有该时间范围的运限结果时不外推未来一两年。

## 让用户拿到什么

先用一小段回答「最值得了解自己的哪几处」，随后按用户要的主题展开，避免各工具逐份复述。详细请求可用一张短表让区别直观：

| 主题 | 本次盘面支持什么 | 各体系相同／不同处 | 现实中可以怎样对照 |
| --- | --- | --- | --- |
| 用户关心的主题 | 实际关键配置及其传统含义 | 标明具体来源，不强求三系齐全 | 一项可观察行为或可尝试安排 |

这张表按需使用，不是固定填满模板。表后说明最重要的两三处张力及其适用情境；证据不足处直接留空并说明原因。完整画像通常约 1500–2500 字，用户要简版就压缩；只要求三体系某一主题对照时，不扩成全人生报告。

保留本次覆盖、缺失与实际精度；技术回执留在工具结果。健康不作诊断，分数不作成功概率，不以合盘或本命结构决定职业、财富和关系成败。

用户要求完整 JSON、全部时间线或完整文件时，首次各所选工具 `fields=null`，保留默认响应预算；从各自 `result_delivery` 读取原 run，核对业务 payload 的 SHA-256，不为补全文再排一次。

## 发送前核对

- 每个主题有实际证据，来源能区分；没读取的宫位、动态运限和专项没有被写成“已经算到”。
- 分歧留住，缺失不凑齐，三系相同措辞不包装成更高准确率。
- 用户看完能说出两三项有依据的特点与一项现实中可对照的安排，而不只记住一串术语。
