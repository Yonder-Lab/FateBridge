# FateBridge 第三方计算核查（2026-10-09）

## 结论

**不能认定 FateBridge 的全部计算结果正确。** 本次实际运行第三方计算引擎，确认了农历日期错误、紫微运限与目标参考算法不一致、六壬取传及布将问题，以及部分入口把平太阳时标作真太阳时的问题。八字四柱与已抽查的西占天文基础计算表现良好；这不等于解释、评分或所有工具均已核验。

本次只新增核查脚本、原始结果和报告，没有修改生产计算实现。全部输入为合成测试数据。

## 优先处理的具体问题

### 1. 农历底表有 90 天错误

范围是 **1900-01-31 至 2100-02-08**，逐日对照 sxtwl。差异分别集中于：

- 1933-07-22 至 1933-08-20，共 30 天。
- 1954-11-25 至 1954-12-24，共 30 天。
- 1978-09-02 至 1978-10-01，共 30 天。

具体例子：

| 公历日期 | FateBridge | sxtwl / lunar-python / 香港天文台 |
| --- | --- | --- |
| 1933-07-22 | 六月初一 | 闰五月三十 |
| 1954-12-01 | 冬月初六 | 冬月初七 |
| 1978-09-02 | 八月初一 | 七月三十 |

`src/fatebridge/core/almanac.py:532` 依赖 lunardate 0.2.2 的转换表，只做同一引擎的反向转换校验；错误底表也能通过该校验。实际 REST `/api/cn/nongli/time` 返回 HTTP 200，但 1954-12-01 的农历日期错误。依赖农历月日的排盘入口可能受到连带影响；本次没有把所有相关盘逐一穷举。

权威历表：[1933 年](https://www.hko.gov.hk/tc/gts/time/calendar/pdf/files/1933.pdf)、[1954 年](https://www.hko.gov.hk/tc/gts/time/calendar/pdf/files/1954.pdf)、[1978 年](https://www.hko.gov.hk/tc/gts/time/calendar/pdf/files/1978.pdf)。

### 2. 紫微运限直接套用八字地支，未得到参考算法的实际落宫

`src/fatebridge/core/metaphysics/ziwei.py:777` 用节气年和出生公历年计算虚岁；`:796` 直接以目标四柱的地支找流年、流月、流日、流时宫。它没有实现 iztro 所采用的完整运限旋转规则，春节和立春之间还存在年界差异。

复现：1990-05-15 10:00 出生，男，+08:00，关闭真太阳时，目标 2026-10-09 10:00。

| 运限实际落宫地支 | FateBridge | iztro |
| --- | --- | --- |
| 流月 | 戌 | 卯 |
| 流日 | 辰 | 未 |
| 流时 | 巳 | 子 |

另例：同一出生日期、女，目标 2026-02-05，FateBridge 虚岁 37，iztro 虚岁 36；流年宫分别为午、巳。

核查取 iztro 的运限 `.index` 并映射本命宫，**没有把 `.earthlyBranch` 当作实际落宫**。其流月、流日、流时的该字段表示历法干支；现有交叉测试只对照这个字段和四化，未验证实际落宫。这是已有测试通过却仍存在差异的原因之一。

晚子时单独处理：FateBridge 本命盘符合 `dayDivide='current'`，对齐后 400 张本命盘的已比较字段全部一致，因此不能把默认规则下的 80 张差异直接称为本命排盘错误。运限差异在两种晚子规则下都存在。iztro 额外包含的天空、截路、空亡三颗星未计入一致性结论。

参考：[iztro 项目](https://github.com/SylarLong/iztro)、[使用说明](https://iztro.com/quick-start)。

### 3. 六壬的三传规则与布将需要系统复核

对照时输入相同日干支、时干支、月将和贵人选项，且已确认天地盘及四课上神一致，因此差异并非仅由历法入口造成。

复现：2026-09-01 10:00，+08:00，关闭真太阳时，戊寅日、丁巳时、处暑，伏吟课。

- FateBridge 三传：**巳 → 寅 → 巳**。
- kinliuren 三传：**巳 → 申 → 寅**。

代码中有可定位的问题：`src/fatebridge/core/metaphysics/liureng.py:229` 按下神地支五行判断上下生克；第一课传入的是日干寄宫，导致戊土被按寄宫巳火处理。寄宫用于定位置，不能取代日干本身的五行。取传实现也需要复核伏吟、返吟、贼克等规则的优先级与细分条件。

`:548` 将天盘位置与按地支构造的贵人序列直接组合；贵人的地盘落位与顺逆判断需要一起核对，不能只改显示顺序。240 组中天将对应关系有 218 组与参考不同。

实际参考源码固定在 [kinliuren，提交 11f7855](https://github.com/kentang2017/kintaiyi/blob/11f78555d5e77c81ac8af69d243a981c22934733/src/kintaiyi/kinliuren.py)。单个参考实现不等于所有流派的权威，但这些差异及可见代码问题足以说明当前结果不能直接视作已验证。

### 4. 多个入口遗漏真太阳时的均时差

`src/fatebridge/services/metaphysics.py:92` 的共享分析种子使用 `LONGITUDE_ONLY`，只修正经度差；`:164` 却标记为“真太阳时”。奇门、六壬、太乙、金口诀等专用分析入口使用这一种子，而八字与紫微本命盘使用包含均时差的口径，造成同输入时辰不一致。

复现：2026-11-03 00:50，+08:00，东经 120°、北纬 30°，开启真太阳时。

- Skyfield/JPL 太阳时角对应约 **01:06:26.6**，应进入丑时。
- FateBridge 八字入口修正约 +16.35 分钟，为 **己丑**。
- 共享分析入口修正 0 分钟，仍为 00:50、**戊子**，响应标签却是“真太阳时”。

经度修正后的平太阳时本身可以是一种明确选择的口径，但不能在缺少均时差时标作真太阳时。该错误已通过奇门 REST 入口重现，原始请求与响应保存于结果文件。

参考：[Skyfield 坐标与时角](https://rhodesmill.org/skyfield/coordinates.html)、[JPL 星历](https://ssd.jpl.nasa.gov/planets/eph_export.html)。

## 需要区分的结论与限制

- **太乙属于待核验版本漂移。** 当前上游与项目历史快照的主算、客算、始击实现不同；100 组里 59 组不同。项目内旧快照测试一致，不能据此证明当前结果正确，也不能仅凭上游更新认定旧版错误。需要确定采用的典籍、表格和版本，再做裁定。
- **规则需要明示。** 紫微晚子时、八字换日、春节/立春年界以及真太阳时口径不可混为一谈；不同入口应暴露并落实各自约定。
- **测试通过不等于外部准确性通过。** 本次完整测试为 911 passed、82 skipped、3 warnings；其中 81 项跳过涉及固定环境的 golden 字节比较。详情见 `results/pytest.txt`。
- **尚未逐一验证的内容**包括完整奇门盘、金口诀、六爻纳甲、梅花、河洛、参评、宿曜，以及西占中间宫头、主限、法达、黄道释放、寿命等高级推运；合婚评分、喜用格局和解释文字也没有由本次天文/历法一致性对照认证。
- 本次 REST 验证通过本地 FastAPI TestClient 完成，四个问题样例都返回 200；这说明错误能到达公开响应，并不代表线上部署或前端展示已核验。
